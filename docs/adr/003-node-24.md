# ADR 003 — Node 24 (não Node 22) em desenvolvimento, CI e container

- **Status:** aceita
- **Data:** 2026-09-05 (Dia 1 — decisão retroativa, formalizada como ADR no Dia 5,
  Tarefa 4; commit original: `1482497`)

## Contexto

O `docs/PLANO.md` original (seção 8) previa **Node 22** para o serviço `app` do
`docker-compose.yml` e para os jobs de CI — era a versão LTS ativa no momento do
planejamento, uma escolha conservadora e razoável.

Na prática, ao rodar `npm ci` dentro do container `node:22-alpine` (e, no CI, no job
`quality`/`test` com `actions/setup-node@v4` fixado em `node-version: 22`), o comando
falhava com `Missing: magicast@0.3.5 from lock file`. A causa raiz: o `package-lock.json`
do projeto foi gerado no host de desenvolvimento com **npm 11** (que acompanha versões
recentes do Node), e o Node 22 traz **npm 10** por padrão. O npm 10 não reconcilia a
estrutura de `overrides`/metadados de dependência que o npm 11 escreve no
`package-lock.json` — apesar de os dois declararem o mesmo `lockfileVersion: 3`, o
formato interno mudou o suficiente entre as duas versões do npm para que `npm ci`
(que é estrito por design, ao contrário de `npm install`) recuse-se a prosseguir.

Duas saídas possíveis: regenerar o `package-lock.json` com npm 10 (perdendo a árvore de
dependência que o host já validava) ou subir a versão do Node usada em
container/CI/`engines` para uma que traga npm 11. A segunda é reversível e não toca no
lockfile; a primeira exigiria revalidar o lockfile inteiro sem necessidade real.

## Decisão

Usamos **Node 24** (LTS) em todo lugar onde a versão do Node é declarada:

- `docker-compose.yml` — serviço `app`, imagem `node:24-alpine`;
- `Dockerfile` — os três estágios (`deps`, `builder`, `runner`) em `node:24-alpine`;
- `.github/workflows/ci.yml` — `actions/setup-node@v4` com `node-version: 24` nos
  quatro jobs (`quality`, `test`, `e2e`, `docker`);
- `.nvmrc` — `24`, para quem usa `nvm`/`fnm` localmente;
- `package.json` — `"engines": { "node": ">=24" }`, para que `npm install`/`npm ci` avise
  (não bloqueia, por padrão do npm) quem tentar rodar numa versão menor.

Node 24 traz **npm 11.19.0** por padrão — a mesma major do npm usada para gerar o
`package-lock.json` no host de desenvolvimento. O `package-lock.json` em si **não foi
alterado nem regenerado**: a decisão resolve a incompatibilidade trocando a versão do
Node (que traz o npm compatível), não o lockfile.

## Alternativas consideradas

**Regenerar o `package-lock.json` com npm 10 (mantendo Node 22).** Manteria a versão
planejada originalmente, mas exigiria rodar `npm install` com npm 10 e revisar a árvore
de dependência resultante inteira (possíveis resoluções de versão diferentes das que o
npm 11 escolheu) — um risco maior e um trabalho maior do que trocar um número de versão
de imagem base, para um projeto de 5 dias sem motivo de negócio para ficar em Node 22
especificamente.

**Fixar `npm install --legacy-peer-deps` ou usar `npm install` em vez de `npm ci`.**
Resolveria o build, mas abriria mão da garantia que `npm ci` dá (instalação
determinística, idêntica ao lockfile, que falha ruidosamente em vez de silenciosamente
resolver diferente) — exatamente a propriedade que se quer ter em CI e num `Dockerfile`
de produção. Rejeitada por trocar uma garantia de reprodutibilidade por conveniência de
curto prazo.

**Fixar a versão exata do npm dentro da imagem (`npm install -g npm@11` antes do
`npm ci`, mantendo Node 22).** Funcionaria, mas adiciona um passo extra em todo lugar
onde a imagem é usada (Dockerfile, CI, `docker-compose.yml`) só para compensar uma
versão de Node que já não traz o npm certo — mais frágil e mais verboso do que
simplesmente usar a imagem `node:24-alpine`, que já vem com o npm correto.

## Consequências

**Positivas**

- `npm ci` volta a funcionar de forma idêntica em container, CI e no host de
  desenvolvimento — os três ambientes usam a mesma major do npm que gerou o lockfile.
- Nenhuma revalidação de árvore de dependências foi necessária: o lockfile commitado
  continua sendo exatamente o que o `npm install` original produziu.
- Node 24 é a LTS mais recente disponível no momento da decisão — não é uma versão de
  transição nem uma major "de teste"; o projeto não fica preso numa versão perto do fim
  de suporte.
- A decisão é visível e centralizada em quatro arquivos fáceis de auditar
  (`.nvmrc`, `package.json#engines`, `docker-compose.yml`, `Dockerfile`,
  `.github/workflows/ci.yml`) — qualquer pessoa que clone o repositório e rode
  `nvm use` (ou preste atenção ao aviso de `engines`) pega a versão certa sem precisar
  ler esta ADR primeiro.

**Negativas e dívidas conhecidas**

- **Divergência do plano original documentada em mais de um lugar.** `docs/PLANO.md`
  (fora do repositório git, arquivo de planejamento) ainda registra "Node 22" na seção 8
  como estava no dia em que foi escrito — é um artefato de planejamento, não o
  README/infra reais (que já refletem Node 24 desde o commit `1482497`), então não foi
  corrigido retroativamente; esta ADR é o registro formal do desvio para quem comparar
  os dois documentos.
- **Acoplamento entre "versão do Node" e "versão do npm que o lockfile espera" não é
  validado automaticamente.** Se alguém regenerar o `package-lock.json` outra vez num
  host com uma versão de npm diferente, o mesmo tipo de incompatibilidade pode se
  repetir — não há hoje um `engines.npm` declarado nem uma checagem de CI que compare a
  versão do npm usada para gerar o lockfile com a versão disponível no ambiente de
  build. Mitigação possível, não feita por estar fora do escopo desta correção: adicionar
  `"engines": { "npm": ">=11" }` ao `package.json`.
- **Imagens `node:24-alpine` são mais recentes e menos "batidas" em produção do que
  `node:22-alpine`** no momento desta decisão — troca aceitável dado que o problema
  concreto (`npm ci` falhando) é mais urgente do que a preferência abstrata por uma
  imagem mais madura.
